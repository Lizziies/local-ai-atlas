First: what is local AI?

“Local” simply means the model inference runs on hardware you control instead of sending every prompt to a remote model provider.

🏠

Local = on your device

The model weights live on your machine. With the right runtime, prompts can be processed locally. Internet access is not inherently required for the model itself.

🔐

Privacy is a property, not magic

A local model can keep prompts on-device, but your surrounding application may still connect to the internet. Check telemetry, plugins and web tools separately.

🧠

Small ≠ bad

A well-trained 4B or MoE model can be remarkably capable. Larger models usually buy you more reasoning depth, coding robustness or multimodal skill — at a higher memory and speed cost.

What changes when you quantize?

Quantization stores weights with fewer bits. Think of it as compressing a huge model so it consumes less memory. Lower precision can increase the models you can run locally, but exact quality and memory trade-offs depend on the model.

FP16~2 bytes/parameter. High memory use, usually the quality reference.
Q8~1 byte/parameter. Often close to full precision, but still memory hungry.
Q4~0.5 byte/parameter. The mainstream sweet spot for many local setups.
2-bit / ternaryExtremely compact. Specialized formats can preserve surprising capability, but require model/runtime support.
Golden rule: model file size is not the same as total runtime memory. Context length, KV cache, vision encoders/projectors and runtime buffers all consume additional memory.

Cloud vs local: a more useful comparison.

Think in capability bands, not “this local model equals that cloud model.” Cloud frontier systems can still have major advantages in long-horizon agents, tool ecosystems, latency, multimodal breadth or raw benchmark ceilings. Local models trade some of that for control and hardware economics.

The beginner path.

No coding degree required. You can get from “I have a GPU” to “I’m running a model locally” in a few clear steps.

1

Find your VRAM

Open your GPU control panel, Task Manager, or vendor specs. VRAM is dedicated GPU memory — different from normal system RAM.

2

Pick a model + quantization

Start with Q4 unless you have a reason not to. Leave headroom for context and the application. On small GPUs, extremely low-bit models such as Bonsai 2 27B (5.95 GB file) can change the equation, but they currently need PrismML’s llama.cpp fork rather than stock LM Studio or Ollama.

3

Install a runtime

LM Studio is the easy GUI route. Ollama is excellent for a simple developer workflow. llama.cpp is the flexible power-user route.

4

Test your real prompts

Ask the model to do your actual work: code, summarize a PDF, explain a spreadsheet, translate, brainstorm, or use tools. Your own workload is the final benchmark.

5

Increase context carefully

Longer context can use a lot of KV-cache memory. “Supports 256K” does not mean your 8–12 GB GPU can run 256K quickly or cheaply.

Model, runtime, harness, agent — not the same thing.

The Atlas keeps these layers strictly apart, because most confusion in local AI comes from mixing them up.

Layer 1 · Model

Model

The trained neural network: weights plus architecture (parameters, experts, context length, modalities).

Qwen3.8 27B · Gemma 4 12B · gpt-oss-20b
Not the app you chat in, and not the software that runs it.
Layer 2 · Runtime

Runtime

Software that loads the weights and executes them on your hardware: quantised formats, GPU/CPU split, KV cache, an API endpoint.

llama.cpp · LM Studio · Ollama · vLLM · SGLang · MLX
A runtime produces tokens; it does not decide what to do.
Layer 3 · Harness

Harness

The layer that wraps a model in an agent loop: prompts, tool registry, permissions, context management, planning, sub-agents.

Qwen Code · OpenCode · Goose · OpenHands · Cline · DeepSeek Harness
Not a model and not a runtime. It connects to a runtime or a cloud API.
Layer 4 · Agent

Agent

The running system that acts on a task: model + runtime + harness + tools working together.

Qwen Code driving Qwen3-Coder-Next served by llama.cpp
A behaviour of the whole stack, not a downloadable file.
Protocol

MCP

Model Context Protocol: an open protocol for exposing tools, resources and prompts from servers to AI applications (clients).

A filesystem server · a database server
Not a security guarantee: review what each server can access.
Capability

Skills

Reusable instructions, scripts and workflows an agent can load on demand for a specific kind of task.

A code-review skill · a release-notes skill
Different from MCP tools (callable capabilities) and from memory (state).
State

Memory

Information an application persists across sessions and feeds back into context: notes, preferences, project facts.

A project notes file loaded at session start
Not the model’s weights, the context window or the KV cache.
Retrieval

RAG

Retrieval-Augmented Generation: fetch relevant passages from an external index at question time and put them into the prompt.

Search your PDFs, then answer from the retrieved chunks
Supplies context; it does not change the model or replace memory.

What is an agent?

A practical agent loop repeatedly observes state, reasons, acts through tools and verifies the result.

1️⃣

Observe

Files, browser state, terminal output, APIs or user context.

2️⃣

Plan

Select the next action, optionally with explicit planning/reasoning.

3️⃣

Act

Call tools, edit files, execute commands or invoke APIs.

4️⃣

Verify

Inspect output, test, recover from errors and continue.

MCP Universe.

Protocol-level interoperability for exposing tools and resources to AI applications.

🔌

Client

The AI app/harness connects to MCP servers and makes capabilities available to the model.

🖥️

Server

A server exposes tools, resources or prompts and can wrap files, databases or services.

🛡️

Trust boundary

MCP is not a security guarantee. Review permissions, secrets, commands and data exposure.

Memory, context & RAG.

Four concepts that are often mixed together.

Context window

Tokens supplied to the model for the current request/session.

KV cache

Runtime attention state that consumes memory as context grows.

Memory

Information an application persists across interactions.

RAG

Retrieve relevant external information and inject it into context.

Hardware Lab.

VRAM is only one part of local inference.

🎮 GPU / VRAM

Weights + KV cache + runtime buffers + vision modules compete for fast memory.

🧠 System RAM

CPU offload can make larger models possible, but memory bandwidth can reduce token speed.

💾 Storage

Keep room for multiple quantizations, caches and updates.

🌡️ Thermals

Sustained inference is a real workload. Cooling and power limits affect clocks and speed.

⚡ PCIe / bandwidth

Moving data between system RAM and GPU is far slower than keeping active tensors in VRAM.

🪟 OS / backend

CUDA, ROCm, Metal and CPU paths have different support and optimization profiles.

Runtime universe.

The runtime decides which file formats load and whether a model can spill into system RAM. Model format and backend compatibility matter as much as the desktop app.

Quantization Lab.

Lower precision can make otherwise impossible local deployments practical.

FP16 / BF16

High precision and high memory.

FP8

Lower precision used in modern serving and model variants.

Q8

Roughly one byte per parameter for weight storage before overhead.

Q4 / low-bit

Much smaller weights; exact quality and speed depend on quantizer and backend.

Remember: file size ≠ runtime memory

KV cache, temporary tensors, vision encoders, metadata and framework overhead all add to the actual footprint.

How the recommender decides.

Every suggestion can be traced to numbers you can check.

01 · Separate budgets

Usable VRAM (minus a driver/desktop reserve) and usable system RAM (minus an OS reserve) are separate budgets. Unified memory is one pool.

02 · Real footprint

Weights (measured file size) + KV cache (from layer count, KV heads and head size in the model’s config, capped for sliding-window layers) + vision projector + runtime buffers.

03 · Tiers

Fits comfortably (≤ 90% of usable GPU memory), fits, tight, possible with offload (dense layer offload or MoE expert offload), not recommended.

04 · Explained ranking

Fit first, then documented task focus, runtime support, quantisation precision and a parameter-count capacity proxy. Each card shows its point breakdown. No invented benchmark scores.

Heuristics, stated openly

Reserves, the 90% comfort line, the 75% unified-memory share and the runtime-overhead term are heuristics, listed in every API response under assumptions. Speed classes are qualitative unless you enter memory-bandwidth figures, in which case only a theoretical upper bound is shown.
